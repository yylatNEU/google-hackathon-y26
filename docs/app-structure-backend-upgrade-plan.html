ParkPulse App Structure and Backend Migration Plan

Current repository analysis, runtime ownership, dataflow pipeline map, migration risks, and a practical sequence for finishing the Spring backend authority shift.

Generated: 2026-06-04 Workspace: google hackathon y26 Primary goal: Spring owns backend authority

Executive Summary

ParkPulse is a hybrid app with a React/Vite frontend, a large FastAPI Python backend, and a newer Java Spring Boot backend that is being promoted as the authoritative backend. The current migration direction is sound: keep SQLite as the shared platform registry, move authority-sensitive routes into Spring, and leave agent intelligence or simulation-heavy Python paths behind the Spring fallback gateway until they are ready.

Recommended next move: make the browser and deployment entrypoint prefer Spring, then migrate Dataflow job launch/status control into Spring. This closes the biggest dataflow pipeline gap without forcing an unsafe rewrite of Python agent intelligence.
Wiring issue: the frontend API discovery currently defaults to http://127.0.0.1:8000 and http://127.0.0.1:8017. Spring runs on 8010 by default, so the app can still talk directly to Python unless VITE_API_URL, NEXT_PUBLIC_API_URL, or same-origin deployment routing points at Spring.

Current Backend Setup

Spring

Authority Layer

Runs with scripts/run_spring_backend.sh on default port 8010. It uses Spring Boot, MVC, JDBC, SQLite, Bouncy Castle, and Google auth.

It should be the first backend endpoint clients call during migration.

Python

Fallback and Intelligence Layer

FastAPI remains available on default port 8000. Spring forwards unmigrated /api/** and /readyz/deep requests through a controlled proxy.

This keeps development moving while route groups migrate one at a time.

Frontend

Client Entry Path

The API client supports configured URLs and role tokens, but local defaults still point at Python-oriented ports. This should be adjusted once Spring is the desired local gateway.

Dataflow Pipeline Analysis

The dataflow pipeline is moving in the right direction: Spring now records canonical events, mirrors dispatch/ack/approval/partner callback state, and can export event rows into BigQuery. That gives the platform a single authoritative event schema for analytics and model feedback.

Event envelope Spring EventPipelineService Stable enough for downstream analytics. Keep schema versioned.

BigQuery analytics sink Spring REST insertAll behind explicit env gates Good for event export. Add dead-letter accounting if live BigQuery failures increase.

Risk and Gating Analysis

Strong

Authority Gates Already Present

  • Spring-owned route fallback gate blocks accidental Python handling for migrated routes.
  • Delivery creation requires role capability and policy-gate/tool-executor boundaries.
  • Live GCP adapters require explicit environment gates, project config, and credentials.
  • Receiver callbacks can require x-parkpulse-receiver-token.
Needs Attention

Gating Gaps

  • Frontend can still call Python first in local defaults.
  • Catch-all fallback remains broad, so unmigrated mutable routes need inventory and ownership labels.
  • Some old Python handshake helper routes remain reachable unless they are deliberately kept as demo-only.
  • Dataflow job control lacks a Spring admin gate because it has not been implemented yet.
Efficient

Efficiency Wins

  • Spring reduces Python hot-path pressure for trust, delivery, event, and gateway paths.
  • SQLite remains enough for the platform registry and local authority records.
  • JSONL ledgers keep migration simple and audit-friendly.
Watch

Efficiency Risks

  • Python monolith still imports many heavy modules at API startup.
  • Frontend retries multiple API bases, which can add latency when the preferred backend is not first.
  • Local JSONL ledgers need rotation/compaction if event volume grows.

Migration Plan

  1. Make Spring the visible app gateway. Add http://127.0.0.1:8010 to local frontend API defaults, or set VITE_API_URL and deployment routing so browser calls hit Spring first.
  2. Add Spring Dataflow job control. Implement a gated DataflowJobLauncherService with Flex Template launch/status routes, fake-server tests, env gates, and fallback ownership blocks.
  3. Inventory remaining Python mutable routes. Label each route as keep-in-Python, migrate-to-Spring, or demo-only. Prioritize state mutation, action, live feed load, and review decision routes.
  4. Migrate park state read models next. Move low-risk read routes such as state-lite, live-summary, scenarios, integration status, and monitoring summaries before mutating routes.
  5. Migrate action and live feed write paths only with parity gates. For each route group, require response parity, auth parity, idempotency, audit receipt, rollback path, and load smoke tests.
  6. Keep AI reasoning services behind contracts. Do not rewrite Gemini, Vertex, Mongo memory, and digital twin internals until the Spring contract boundary is stable.
  7. Harden ledgers for production volume. Add JSONL rotation, replay checkpoints, dead-letter rows, and dashboardable export failure counters.

Go/No-Go View

Recommendation: go with conditions for continued demo and staged migration. The core migration pattern is correct, but production authority should wait until frontend routing prefers Spring and Dataflow launch/status is gated in Spring.
  • Go: SQLite remains enough for the current app platform registry and migration ledger needs.
  • Go: Spring is a better authority layer than FastAPI for durable backend contracts, route gating, typed service boundaries, and long-lived operational APIs.
  • Condition: make Spring the first backend endpoint from the frontend and deployment ingress.
  • Condition: close the Dataflow orchestration gap before calling the dataflow pipeline fully Spring-owned.
  • Condition: keep Python AI modules behind contracts rather than migrating them all at once.
